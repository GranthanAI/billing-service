# GranthanAI billing-service LLD

Nov 1, 2026 · @ShubhChi

Low-level design for the billing-service in Doc: the code, tables, scripts, APIs and jobs needed to build v1 (Free, Pro, Max), with the hooks for organisations and Pay as you Go already in place.

## Scope, conventions and libraries

One repository, `billing-service`, builds one container image that runs as two processes: `billing-api` (REST + gRPC) and `billing-worker` (Kafka consumers, outbox relay, jobs). v1 covers Free, Pro and Max; the organisation and Pay as you Go parts are in the schema and marked v2 or v3.

### Conventions

- **Money.** Charges are `int` paise (`BIGINT`). AI cost is `int` micro-rupees (₹1 = 1,000,000). No `float` anywhere money is stored or compared; `Decimal` only inside rating, rounded once at the end.
- **Rounding.** Half-up, done once per computed amount by `round_half_up(numerator, denominator)` in integer arithmetic.
- **Time.** Stored as `timestamptz` in UTC. Business days (daily limits, invoice dates, financial year) use Asia/Kolkata. All code reads time through an injected `Clock`, never `datetime.now()`.
- **IDs.** UUIDv7 for rows created here (time-ordered, index-friendly); gateway IDs kept as `text` exactly as Razorpay sends them.
- **Writes.** Every use case runs in one database transaction, and writes its outgoing events to the `outbox` table in that same transaction.

## Domain model

A subscription is a logical contract that outlives any single Razorpay mandate. Razorpay cannot update UPI or eMandate subscriptions, so each plan change swaps the mandate underneath while the `subscriptions` row, its history and its invoices stay the same.

### Core types

| Type | Kind | Fields / values |
| --- | --- | --- |
| `Paise`, `MicroInr` | value object (`NewType` over `int`) | arithmetic only with the same type; conversions explicit |
| `ModelGroup` | enum | `fast`, `smart`, `best`, `ultra` |
| `Interval` | enum | `month`, `year` |
| `OwnerType` | enum | `user`, `org` |
| `OrgVariant` | enum | `college`, `company` |
| `Limits` | frozen dataclass | every limit in the plan sheets; `-1` = unlimited |
| `PlanVersion` | frozen dataclass | `plan_code`, `version`, `rank`, prices, `Limits`, allowed models |
| `Grant` | frozen dataclass | `source` (override / org / subscription / free), `plan_version`, `billing_account_id`, `subscription_id`, `variant` |
| `Entitlement` | frozen dataclass | the winning `Grant` + its resolved `Limits`, models and a content hash |
| `Hold` | frozen dataclass | `hold_id`, `user_id`, `kind`, `group`, `price_paise`, `day`, `expires_at` |
| `Posting` | frozen dataclass | `account_code`, signed `amount_paise` (debit +, credit −) |

### Subscription states

This refines the design doc's diagram with a `suspended` state: after the 3-day grace the user is on Free limits, but Razorpay may still be retrying the charge, and a late success must restore the plan.

| Status | Grants the plan? | Meaning |
| --- | --- | --- |
| `incomplete` | No | Checkout started; mandate not yet authorised |
| `active` | Yes | Paid for the current period |
| `past_due` | Yes | Renewal failed; inside `grace_until` |
| `suspended` | No (Free) | Grace over; Razorpay still retrying |
| `cancelling` | Yes | Cancelled at period end |
| `ended` | No | Terminal: cancelled, halted, completed or abandoned |

### Transitions

The transition table in `domain/subscription.py` is the only place status changes. A trigger not listed for the current status raises `IllegalTransition`, which the webhook processor logs and ignores, so late or out-of-order events cannot move a subscription backwards.

| From | Trigger | To | Side effects in the same transaction |
| --- | --- | --- | --- |
| `incomplete` | first charge captured | `active` | period set; payment, invoice, ledger; `subscription.changed` |
| `incomplete` | not authorised within 24 h | `ended` | cancel at Razorpay |
| `active` | renewal charge captured | `active` | period advanced; payment, invoice, ledger |
| `active` | renewal charge failed | `past_due` | `grace_until = now + 3 days`; `payment.failed` |
| `past_due` | charge captured | `active` | clear grace; `subscription.changed` |
| `past_due` | `grace_until` passed | `suspended` | `subscription.changed` (entitlements to Free) |
| `suspended` | charge captured | `active` | `subscription.changed` |
| `past_due`, `suspended` | Razorpay `halted` | `ended` | cancel at Razorpay; `subscription.changed` |
| `active`, `past_due` | user cancels | `cancelling` | Razorpay cancel at cycle end |
| `cancelling` | period end reached | `ended` | `subscription.changed` |
| `active` | upgrade paid | `active` | `plan_version_id` and mandate switched now; period restarts; old period's unused days refunded |
| `active` | downgrade requested | `active` | `pending_plan_version_id` set; applied at period end |
| any live | user cancels from UPI app or bank | `cancelling` | access kept to period end |

A cancelled Razorpay subscription cannot be reactivated, so "resume" from `cancelling` authorises a new mandate starting at the period end and returns the row to `active`.

### Razorpay status mapping

| Razorpay status | Our status |
| --- | --- |
| `created`, `authenticated` (first mandate) | `incomplete` |
| `authenticated` (next mandate, future start) | unchanged; stored as `next_gateway_subscription_id` |
| `active` | `active` |
| `pending` | `past_due`, or `suspended` once grace has passed |
| `halted` | `ended` |
| `cancelled` | `cancelling` if before period end, else `ended` |
| `completed`, `expired` | `ended` |
| `paused` | `suspended` |

## Database schema

Everything lives in a `billing` schema on PostgreSQL 17, owned by a migration role. The app role gets `SELECT, INSERT` on append-only tables and `UPDATE` only where state legitimately changes. Two departures from the design doc: holds live only in Valkey (they last at most 10 minutes, so the `reservations` table is dropped), and `usage_events` is keyed on its source ID plus `occurred_at`, because a partitioned table's unique key must include the partition column.

### Guards in the database

```sql
-- append-only tables
CREATE FUNCTION forbid_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION '% is append-only', TG_TABLE_NAME;
END $$;

CREATE TRIGGER ledger_entries_append_only BEFORE UPDATE OR DELETE ON ledger_entries
  FOR EACH ROW EXECUTE FUNCTION forbid_change();
CREATE TRIGGER ledger_tx_append_only BEFORE UPDATE OR DELETE ON ledger_transactions
  FOR EACH ROW EXECUTE FUNCTION forbid_change();
CREATE TRIGGER usage_events_append_only BEFORE UPDATE OR DELETE ON usage_events
  FOR EACH ROW EXECUTE FUNCTION forbid_change();

-- every ledger transaction sums to zero, checked at commit
CREATE FUNCTION assert_ledger_balanced() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (SELECT sum(amount_paise) FROM ledger_entries
      WHERE transaction_id = NEW.transaction_id) <> 0 THEN
    RAISE EXCEPTION 'ledger transaction % does not balance', NEW.transaction_id;
  END IF;
  RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER ledger_balanced AFTER INSERT ON ledger_entries
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_ledger_balanced();

REVOKE UPDATE, DELETE ON ledger_entries, ledger_transactions, usage_events FROM billing_app;
```

Old `usage_events` partitions are detached and archived to object storage after 13 months; dropping a partition is not a row `DELETE`, so the trigger does not block it.

## Valkey keys and Lua scripts

Four scripts do all counter and hold changes, each atomic, so two tabs racing at 59 of 60 messages cannot both pass. Valkey runs as a single instance with `appendonly yes`, `appendfsync everysec` and `maxmemory-policy noeviction`: an evicted counter would hand out free messages. At \~1 KB per active user, 12,000 users fit in about 12 MB.

### Keys

| Key | Type | TTL | Holds |
| --- | --- | --- | --- |
| `ent:{uid}` | string (JSON) | 10 min; deleted on `subscription.changed` | Entitlement snapshot |
| `use:{uid}:d:20261101` | hash: `total`, `fast`, `smart`, `best`, `ultra`, `grace` | 48 h | Daily counters for one IST calendar day |
| `use:{uid}:m:202611` | hash: `total`, `youtube` | 40 days | Monthly counters (YouTube videos) |
| `hold:{uid}:<hold_id>` | hash: `counters`, `field`, `price`, `mode` | hold TTL + 1 h | One open hold |
| `holds:due` | sorted set; member `uid:hold_id`, score = expiry | none | Queue for the expiry sweeper |
| `idem:{uid}:<key>` | string | 24 h | Stored ALLOW result, replayed on retry |
| `done:{uid}:<source_id>` | string | 24 h | Guards against committing one usage twice |
| `wal:{account}` | hash: `balance`, `held`, `mtd`, `cap` | none | v3: wallet mirror of the ledger |

`{uid}` is a hash tag, so a move to Valkey Cluster later keeps each user's keys in one slot; `holds:due` would then be split per slot.

### reserve.lua

```lua
-- KEYS: 1 counters  2 idem  3 hold  4 wallet  5 holds:due
-- ARGV: 1 mode ('plan'|'payg')  2 field (group or 'youtube')  3 limit (-1 = none)
--       4 best_limit (-1 = none)  5 price_paise  6 hold_id  7 now (unix s)
--       8 hold_ttl  9 counter_ttl  10 no_credit_fast_per_day  11 uid
--       12 billing_account_id  13 plan_version_id (stored on the hold for attribution)
local prior = redis.call('GET', KEYS[2])
if prior then return prior end                       -- replay a retried ALLOW

local mode, field = ARGV[1], ARGV[2]
local limit, best_limit = tonumber(ARGV[3]), tonumber(ARGV[4])
local price, hold_id, now = tonumber(ARGV[5]), ARGV[6], tonumber(ARGV[7])
local hold_ttl, counter_ttl, grace = tonumber(ARGV[8]), tonumber(ARGV[9]), tonumber(ARGV[10])
local total = tonumber(redis.call('HGET', KEYS[1], 'total') or '0')
local downgraded = 0

if mode == 'plan' then
  if limit >= 0 and total >= limit then return 'DENY|LIMIT' end
  if field == 'best' and best_limit >= 0 then
    local best = tonumber(redis.call('HGET', KEYS[1], 'best') or '0')
    if best >= best_limit then field = 'smart'; downgraded = 1 end
  end
  price = 0
else
  local w = redis.call('HMGET', KEYS[4], 'balance', 'held', 'mtd', 'cap')
  local balance, held = tonumber(w[1] or '0'), tonumber(w[2] or '0')
  local mtd, cap = tonumber(w[3] or '0'), tonumber(w[4] or '-1')
  if cap >= 0 and mtd + held + price > cap then return 'DENY|SPEND_CAP' end
  if balance - held < price then
    if field ~= 'fast' then return 'DENY|NO_CREDIT' end
    if tonumber(redis.call('HGET', KEYS[1], 'grace') or '0') >= grace then
      return 'DENY|NO_CREDIT'
    end
    redis.call('HINCRBY', KEYS[1], 'grace', 1)       -- free Fast message, no credit
    price = 0
  elseif price > 0 then
    redis.call('HINCRBY', KEYS[4], 'held', price)
  end
end

redis.call('HINCRBY', KEYS[1], 'total', 1)
redis.call('HINCRBY', KEYS[1], field, 1)
redis.call('EXPIRE', KEYS[1], counter_ttl)
redis.call('HSET', KEYS[3], 'counters', KEYS[1], 'field', field, 'price', price, 'mode', mode,
           'acct', ARGV[12], 'pv', ARGV[13])
redis.call('EXPIRE', KEYS[3], hold_ttl + 3600)
redis.call('ZADD', KEYS[5], now + hold_ttl, ARGV[11] .. ':' .. hold_id)
local result = 'ALLOW|' .. field .. '|' .. hold_id .. '|' .. price .. '|' .. downgraded
redis.call('SET', KEYS[2], result, 'EX', 86400)
return result
```

Denies are not stored, so a user who tops up and retries is not refused from a stale answer.

### commit.lua

Run by the usage consumer after its Postgres transaction commits.

```lua
-- KEYS: 1 hold  2 wallet  3 holds:due  4 done marker  5 counters for the usage's IST day
-- ARGV: 1 due member  2 charged_paise (0 unless paid from credits)  3 model group  4 counter_ttl
if not redis.call('SET', KEYS[4], '1', 'NX', 'EX', 86400) then return 'DUP' end
local held = redis.call('HGET', KEYS[1], 'price')
if held then
  if tonumber(held) > 0 then redis.call('HINCRBY', KEYS[2], 'held', -tonumber(held)) end
else
  -- the hold expired and its message was given back; the answer came anyway, so count it
  redis.call('HINCRBY', KEYS[5], 'total', 1)
  redis.call('HINCRBY', KEYS[5], ARGV[3], 1)
  redis.call('EXPIRE', KEYS[5], tonumber(ARGV[4]))
end
local charged = tonumber(ARGV[2])
if charged > 0 then
  redis.call('HINCRBY', KEYS[2], 'balance', -charged)
  redis.call('HINCRBY', KEYS[2], 'mtd', charged)
end
redis.call('DEL', KEYS[1])
redis.call('ZREM', KEYS[3], ARGV[1])
return 'OK'
```

### release.lua

Called with `refund` by `Release` (generation failed) and with `expire` by the sweeper (no usage arrived within the hold TTL). Both give the message back and free any held credit (Decision 7); the reason is used only for metrics. If an expired message's usage arrives later, `commit.lua` counts and bills it then.

```lua
-- KEYS: 1 hold  2 counters (read from the hold by the caller)  3 wallet  4 holds:due
-- ARGV: 1 due member  2 reason ('refund' | 'expire'), for metrics only
local h = redis.call('HMGET', KEYS[1], 'counters', 'field', 'price', 'mode')
if not h[1] then
  redis.call('ZREM', KEYS[4], ARGV[1])
  return 'GONE'                                     -- already committed or released
end
if h[1] ~= KEYS[2] then return redis.error_reply('counter key mismatch') end
local price = tonumber(h[3])
if h[4] == 'payg' and price > 0 then redis.call('HINCRBY', KEYS[3], 'held', -price) end
redis.call('HINCRBY', KEYS[2], 'total', -1)
redis.call('HINCRBY', KEYS[2], h[2], -1)
redis.call('DEL', KEYS[1])
redis.call('ZREM', KEYS[4], ARGV[1])
return 'OK'
```

### Sweeper and rebuild

- **Sweeper (every 30 s):** `ZRANGEBYSCORE holds:due -inf <now> LIMIT 0 500`, then `release.lua … expire` for each member. The message is given back and `billing_holds_expired_total` goes up; the "holds leaking" alert catches a pipeline that has stopped billing.
- **Rebuild after Valkey loss:** for today's IST day, `use:*` counters are recomputed from `usage_events` grouped by user and group; `wal:*` from `ledger_balances`. Open holds are lost; at most 10 minutes of in-flight credit-paid messages are charged without a hold, so a wallet can dip slightly below zero and the next top-up covers it.

### Calling the scripts

```python
class ValkeyCounters(Counters):                 # adapters/valkey/counters.py
    def __init__(self, client: valkey.asyncio.Valkey) -> None:
        self._reserve = client.register_script(load("reserve.lua"))  # EVALSHA, NOSCRIPT fallback

    async def reserve(self, r: ReserveArgs) -> ReserveResult:
        raw = await self._reserve(
            keys=[r.counter_key, f"idem:{{{r.uid}}}:{r.idem_key}",
                  f"hold:{{{r.uid}}}:{r.hold_id}", f"wal:{{{r.account}}}", "holds:due"],
            args=[r.mode, r.field, r.limit, r.best_limit, r.price_paise, r.hold_id,
                  r.now_unix, r.hold_ttl, r.counter_ttl, r.no_credit_fast, r.uid, r.account, r.plan_version_id],
        )

```

## Hot path

A message makes two synchronous calls to Valkey through the billing API; everything after the answer is billed asynchronously by the worker.

&#91;embedded content: message path · reserve, generate, commit, release\]

Step 7 is one Postgres transaction (inbox claim, usage row, wallet debit on Pay as you Go, threshold events in the outbox); step 8 runs only after it commits. If no usage event arrives within 10 minutes, the sweeper expires the hold and gives the message back instead of step 8.

### Loader and sync

1. **Parse and validate** with Pydantic: every limit present, prices non-negative, every model listed in `model_prices`, ranks unique per audience. CI fails on any error.
2. **Checksum** each plan (and variant) block. `billing catalog sync` runs as a deploy step: an unchanged checksum is skipped; a changed one inserts a new `plan_versions` row with `version + 1` and `effective_from = now()`, and stamps `retired_at` on the old one.
3. **Razorpay plans** are created by the sync step for each new priced version and interval (Razorpay plans cannot be edited), and their IDs stored on the `plan_versions` row.
4. **Existing subscribers keep their version.** New checkouts use the newest version. Moving existing subscribers to a new price is an explicit admin migration that schedules the change at each subscriber's next renewal, with notice.
5. **Limit-only changes** (no price change) can apply to all subscribers: the sync step flags them, and the admin chooses "apply to existing" which re-points live subscriptions and clears `ent:*`.

Model prices and the FX rate are not in this file: they change on their own schedule and are entered through admin endpoints into `model_prices` and `fx_rates`, with an effective date.

## Internal gRPC API

Service-to-service calls use gRPC on port 50051, reachable only inside the cluster network and authenticated with a service token in metadata (mTLS when the platform adds it). The proto lives in `granthan-contracts`; Buf blocks breaking changes in CI.

```proto
syntax = "proto3";
package granthan.billing.v1;

service BillingInternal {
  // Called before any action that costs money. Idempotent on idempotency_key.
  rpc CheckAndReserve(CheckAndReserveRequest) returns (CheckAndReserveResponse);
  // Gives a reserved unit back when the action failed. Idempotent on hold_id.
  rpc Release(ReleaseRequest) returns (ReleaseResponse);
  // Full limits for services that enforce counts themselves.
  rpc GetEntitlements(GetEntitlementsRequest) returns (Entitlements);
}

enum ModelGroup {
  MODEL_GROUP_UNSPECIFIED = 0;
  MODEL_GROUP_FAST = 1;
  MODEL_GROUP_SMART = 2;
  MODEL_GROUP_BEST = 3;
  MODEL_GROUP_ULTRA = 4;
}

enum ReserveKind {
  RESERVE_KIND_UNSPECIFIED = 0;
  RESERVE_KIND_MESSAGE = 1;
  RESERVE_KIND_YOUTUBE_VIDEO = 2;
  RESERVE_KIND_MANIM_VIDEO = 3;
}

enum DenyReason {
  DENY_REASON_UNSPECIFIED = 0;
  DENY_REASON_DAILY_LIMIT = 1;
  DENY_REASON_MONTHLY_LIMIT = 2;
  DENY_REASON_MODEL_NOT_IN_PLAN = 3;
  DENY_REASON_NO_CREDIT = 4;
  DENY_REASON_SPEND_CAP = 5;
  DENY_REASON_ACCOUNT_BLOCKED = 6;
}

message CheckAndReserveRequest {
  string user_id = 1;
  string idempotency_key = 2;       // request_message_id, or the video id
  ReserveKind kind = 3;
  ModelGroup requested_group = 4;   // messages only
  string requested_model = 5;       // optional; empty lets the router pick
}

message CheckAndReserveResponse {
  bool allowed = 1;
  DenyReason deny_reason = 2;
  string hold_id = 3;
  ModelGroup granted_group = 4;
  bool downgraded = 5;              // Max user past 12 Best messages today
  int32 max_context_tokens = 6;     // 16k / 64k / 128k reading cap
  string billing_account_id = 7;
  string message_key = 8;           // frontend copy key from the Limit Behaviour sheet
  int64 hold_expires_at_unix = 9;
  int32 remaining_today = 10;       // -1 = unlimited
  string funded_by = 11;            // plan | credits
}

message ReleaseRequest {
  string user_id = 1;
  string hold_id = 2;
  string reason = 3;                // provider_error, cancelled, timeout
}
message ReleaseResponse { bool released = 1; }

message GetEntitlementsRequest { string user_id = 1; }

message Entitlements {
  string user_id = 1;
  string billing_account_id = 2;
  string source = 3;                // override | org | subscription | free
  string plan_code = 4;
  int32 plan_version = 5;
  repeated string allowed_models = 6;
  map<string, int64> limits = 7;    // keys as in plans.yaml; -1 = unlimited
  string version_hash = 8;          // changes whenever any field changes
}
```

| RPC | Deadline set by caller | On billing unavailable (caller's breaker open) |
| --- | --- | --- |
| `CheckAndReserve` | 150 ms | conversation-service allows Fast only, 10 a day per user from its own Valkey counter; denies Best and Ultra |
| `Release` | 500 ms, 3 retries | Ignore after retries; the hold expires, which frees the money and gives the message back |
| `GetEntitlements` | 300 ms | Use the last cached response for up to 1 hour, else Free limits |

The `{user_id}` the caller passes comes from the verified JWT at api-gateway and travels in the event; billing never trusts a user ID from a client payload.

### Consumer rules

- Offsets are committed only after the Postgres transaction commits; a crash replays the batch and `processed_events` turns replays into no-ops.
- A failing event is retried in place 5 times with backoff (0.5 s to 8 s), then copied to `billing.usage.dlq` with the error, and the partition moves on. A DLQ message pages you: an unbilled message is lost margin.
- `succeeded = false` on `chat.response.generated` releases the hold (the same as `Release`) and records the helper calls' cost, with `price_paise = 0`.
- Threshold events fire once per limit, per user, per period: the consumer sets `thr:{uid}:<limit>:<period>:<percent>` with `SET NX` before writing to the outbox.

## Core algorithms

Each algorithm below lives in one module and has its own tests; the domain functions are pure and the use cases wrap them in one transaction.

### Entitlement resolution

A user can hold several grants at once: Free, a personal subscription, an organisation seat, Pay as you Go credits and an admin override. An override always wins. Otherwise the highest-ranked paid plan wins, and on a tie the organisation's grant is used, so organisation usage reports stay complete. Pay as you Go is the plan only when there is no paid plan; otherwise the wallet rides on the entitlement as overflow for messages the plan denies (Decision 4).

```python
# domain/entitlements.py
PAID_PRIORITY = {"org": 2, "subscription": 1}
LIVE = {SubStatus.ACTIVE, SubStatus.PAST_DUE, SubStatus.CANCELLING}

def pick(grants: list[Grant]) -> Grant:
    overrides = [g for g in grants if g.source == "override"]
    if overrides:
        return max(overrides, key=lambda g: (g.plan_version.rank, g.expires_at))
    paid = [g for g in grants if g.source in PAID_PRIORITY]
    if paid:
        return max(paid, key=lambda g: (g.plan_version.rank, PAID_PRIORITY[g.source]))
    payg = [g for g in grants if g.source == "payg"]
    return payg[0] if payg else next(g for g in grants if g.source == "free")

# app/reserve.py
async def resolve(user_id: UUID) -> Entitlement:
    if cached := await cache.get(user_id):
        return cached
    now = clock.now()
    grants = [free_grant(user_id)]
    grants += await repo.active_overrides(OwnerType.USER, user_id, now)
    if sub := await repo.subscription_in(OwnerType.USER, user_id, LIVE):
        grants.append(Grant.from_subscription(sub))
    wallet = await repo.wallet_of(OwnerType.USER, user_id)       # v3; None before the first top-up
    if wallet:
        grants.append(Grant.payg(wallet))
    if m := await orgs.membership(user_id):                       # v2
        grants += await repo.active_overrides(OwnerType.ORG, m.org_id, now)
        if m.active and (sub := await repo.subscription_in(OwnerType.ORG, m.org_id, LIVE)):
            grants.append(Grant.from_org(sub, variant=m.org_type))
    ent = Entitlement.of(pick(grants), overflow_wallet=wallet)
    await cache.set(user_id, ent, ttl_s=600)
    return ent
```

### CheckAndReserve

1. `resolve(user_id)`; if the account is blocked, deny with `ACCOUNT_BLOCKED`.
2. If the requested model or group is outside the plan, go to step 4 when the entitlement has a wallet; otherwise deny with `MODEL_NOT_IN_PLAN`.
3. **Plan call.** Build the counter key from the IST date (`use:{uid}:d:YYYYMMDD`, or `:m:YYYYMM` for YouTube) and run `reserve.lua` in `plan` mode with the plan's limits, a new UUIDv7 `hold_id`, the billing account and plan version. An `ALLOW` returns with `funded_by = plan`.
4. **Credits call.** If step 3 returned `DENY|LIMIT` (or step 2 sent the request here) and a wallet exists, run `reserve.lua` again in `payg` mode with the Pay as you Go unit price, the wallet key and `no_credit_fast_per_day = 0` (the free Fast allowance is only for users whose plan is Pay as you Go). An `ALLOW` returns with `funded_by = credits`. Users on Pay as you Go go straight to this call, with the allowance set to 10.
5. Map a final deny to `DAILY_LIMIT`, `MONTHLY_LIMIT`, `NO_CREDIT` or `SPEND_CAP` and attach the copy key; return the granted group, the reading cap and `remaining_today`.

A subscriber within their limits costs one `GET` and one `EVALSHA`; a message paid from credits costs one more `EVALSHA`. Each script is atomic on its own, and the two never need to be atomic together, because the credits call runs only after the plan has already refused.

### Rating

```python
# domain/rating.py
def rate(calls: list[LlmCall], prices: PriceBook, usd_inr: Decimal,
         group: ModelGroup, mode: str, payg: PaygPrices) -> Rating:
    cost_usd = Decimal(0)
    for c in calls:
        p = prices.for_model(c.model)
        uncached = c.input_tokens - c.cached_input_tokens
        cached_price = p.cached_input if p.cached_input is not None else p.input
        cost_usd += (uncached * p.input + c.cached_input_tokens * cached_price
                     + c.output_tokens * p.output) / Decimal(1_000_000)
    cost_micro_inr = int((cost_usd * usd_inr * 1_000_000).to_integral_value(ROUND_HALF_UP))

    if mode == "payg":                                    # paid from credits
        answer = next(c for c in calls if c.purpose == "answer")
        units = max(1, -(-answer.input_tokens // payg.long_message_tokens))   # ceil
        price = units * payg.unit_prices[group]
    else:                                                 # covered by the plan
        units, price = 1, 0
    return Rating(cost_micro_inr, units, Paise(price))
```

The price book and FX rate are those in effect at the event's `occurred_at`. Worked example matching the workbook: a Smart message on Claude Haiku 5.5 (6,000 in, 700 out at $0.10 / $0.50 per 1M) costs $0.00095; the helper calls on gpt-oss-20b (2,600 in, 350 out at $0.075 / $0.30) cost $0.0003. At ₹95 per US$ that is ₹0.11875, stored as 118,750 micro-rupees, the same figure as the Model Prices sheet.

### GST split

```python
# domain/money.py
def round_half_up(numerator: int, denominator: int) -> int:
    return (2 * numerator + denominator) // (2 * denominator)

def split_gst(gross: Paise, supplier_state: str, customer_state: str | None) -> GstSplit:
    taxable = round_half_up(gross * 100, 118)               # prices include 18% GST
    tax = gross - taxable
    if customer_state is None or customer_state == supplier_state:
        cgst = tax // 2
        return GstSplit(taxable, cgst=cgst, sgst=tax - cgst, igst=0)
    return GstSplit(taxable, cgst=0, sgst=0, igst=tax)
```

For Pro at ₹499: taxable ₹422.88, CGST ₹38.06, SGST ₹38.06. The parts always add back to the gross, which the `invoices` check constraint enforces.

### Proration

```python
def unused_credit(paid: Paise, start: datetime, end: datetime, now: datetime) -> Paise:
    """Share of the amount paid for [start, end) that is still unused at `now`."""
    remaining = int((end - now).total_seconds())
    total = int((end - start).total_seconds())
    if remaining <= 0:
        return Paise(0)
    return Paise(round_half_up(paid * remaining, total))
```

Pro to Max monthly with 15 of 30 days left: the user pays ₹1,499 for a Max month starting today, and ₹249.50 of the Pro payment comes back (₹499 × 15/30) with a credit note. `paid` is the amount actually captured for that period, so a discounted period refunds the discounted share. A move to a cheaper total, including yearly to monthly, is a downgrade and waits for the period end.

### Plan change with Razorpay

Because UPI and eMandate subscriptions cannot be updated, every change creates a new mandate:

1. **Upgrade: one checkout, starts now.** Create a Razorpay subscription for the new plan version with no `start_at` and no add-on, and return Checkout options. On its first `subscription.charged`, in one transaction: point the row at the new mandate and plan version, restart the period, record the payment and invoice, enqueue `gateway.cancel` for the old mandate (immediately) and `refund.issue` for `unused_credit` of the old period, and emit `subscription.changed`. `refund.issue` calls Razorpay's refund API and issues a credit note on the `CN` series.
2. **Downgrade.** Create the new mandate with `start_at = current_period_end`, so nothing is charged now. When it is authorised, set `pending_plan_version_id` and cancel the old mandate at cycle end. Nothing changes for the user until the period ends. Run this flow once in Razorpay test mode before launch.
3. **Swap at period end.** The first `subscription.charged` on the next mandate moves `next_gateway_subscription_id` into `gateway_subscription_id`, applies the pending plan, and advances the period. The old mandate's `subscription.cancelled` is recognised as part of the swap, not as a cancellation.
4. **Credits are not used for plan changes.** They pay only for messages and items the plan does not cover.

```sql
INSERT INTO invoice_counters (series, financial_year) VALUES ($1, $2) ON CONFLICT DO NOTHING;
```

### Applying usage

```python
# app/usage.py
async def apply_response(ev: ChatResponseGenerated) -> None:
    hold = await counters.peek_hold(ev.user_id, ev.hold_id)       # None if it already expired
    grant = hold.grant if hold else (await resolve(ev.user_id)).grant
    mode = hold.mode if hold else "plan"                           # late event: billed to the plan
    rating = rate(ev.calls, prices.at(ev.occurred_at), fx.at(ev.occurred_at),
                  ev.model_group, mode, catalog.payg_prices())

    async with uow() as tx:
        if not await tx.processed.claim("billing-usage", ev.envelope.event_id):
            return                                                  # replay
        await tx.usage.insert(UsageEvent.from_(ev, grant, rating))  # ON CONFLICT DO NOTHING
        if rating.price_paise:                                      # paid from credits
            await tx.wallets.debit(hold.account_id, rating.price_paise,
                                   key=f"usage:{ev.request_message_id}")
        await thresholds.enqueue_if_crossed(tx, ev.user_id, grant)
    await counters.commit(ev.user_id, ev.hold_id, rating.price_paise,
                          ev.request_message_id, ev.model_group, ev.occurred_at)
```

`wallets.debit` locks the wallet's `ledger_balances` row, takes credit lots oldest-expiry first, and posts one balanced ledger transaction. If the process dies between the database commit and `commit.lua`, the 5-minute wallet resync corrects the Valkey mirror.

### Webhook processing

```python
# app/webhooks.py, run by the worker for each inbox row
async def process(row: InboxRow) -> None:
    ev = RazorpayEvent.parse(row.payload)
    fresh = await gateway.fetch(ev.entity_type, ev.entity_id)       # outside any transaction
    async with uow() as tx:
        sub = await tx.subs.lock_by_gateway_id(fresh.subscription_id)  # SELECT ... FOR UPDATE
        if ev.has_payment:
            await record_charge(tx, sub, ev.payment)                   # payment, invoice, ledger; idempotent
        trigger = derive_trigger(sub, fresh, ev)
        try:
            apply_transition(tx, sub, trigger)                         # domain table + history + outbox
```

The Razorpay object is fetched before the transaction opens, so no row lock is held across a network call. Retries back off from 30 s to 1 h over 10 attempts; then the row is marked `failed` and alerts.

### Outbox relay

One worker replica holds `pg_try_advisory_lock(hashtext('outbox-relay'))` and runs the relay, which keeps per-key order:

```python
while running:
    async with uow() as tx:
        rows = await tx.fetch("""SELECT id, topic, key, payload, headers FROM outbox
                                 WHERE published_at IS NULL ORDER BY id LIMIT 500""")
        for r in rows:
            producer.produce(r.topic, key=r.key, value=r.payload, headers=r.headers)
        await producer.flush()                  # acks=all, enable.idempotence=true
        await tx.execute("UPDATE outbox SET published_at = now() WHERE id = ANY($1)",
                         [r.id for r in rows])
    await asyncio.sleep(0 if rows else 0.2)
```

A crash after `flush` and before the update republishes the batch; consumers drop the duplicates by `event_id`. Published rows are deleted after 7 days.

## Background jobs

All scheduled and deferred work goes through the `jobs` table, so it survives restarts and runs exactly once even with two worker replicas. A scheduler loop enqueues recurring jobs with a `dedupe_key` naming the slot (for example `reconcile:2026-11-01`), and a duplicate insert by the second replica is a no-op.

### Runner

```sql
-- claim up to 10 ready jobs
UPDATE jobs SET status = 'running', attempts = attempts + 1,
                locked_until = now() + interval '5 minutes'
 WHERE id IN (SELECT id FROM jobs
               WHERE status = 'queued' AND run_at <= now()
               ORDER BY run_at LIMIT 10
               FOR UPDATE SKIP LOCKED)
RETURNING id, kind, payload, attempts, max_attempts;
```

On success the job becomes `done`; on error it goes back to `queued` with `run_at = now() + min(2^attempts, 3600) s`, and to `dead` (with an alert) after `max_attempts`. A reaper requeues `running` jobs whose `locked_until` has passed, which covers a worker killed mid-job. Handlers must be idempotent, because a job can run twice after a crash.

### Idempotency middleware

1. Hash the method, path and body with SHA-256.
2. `INSERT INTO idempotency_keys (scope, key, request_hash, locked_until) VALUES (user, key, hash, now() + 30 s) ON CONFLICT DO NOTHING`.
3. If the row already existed: a different hash returns `IDEMPOTENCY_KEY_REUSED`; a stored response is replayed byte for byte; otherwise `REQUEST_IN_PROGRESS`.
4. Run the handler, then store `status_code` and `response` on the row. A 5xx is not stored, so the client can retry with the same key.

Calls to Razorpay carry their own idempotency: subscription and order creation pass the billing row's ID in `notes`, and a retry first looks the object up by that note before creating another.

### Concurrency rules

- **Isolation.** `READ COMMITTED` plus explicit row locks. No `SERIALIZABLE`; the locks below make the invariants hold.
- **Lock order.** Always `billing_accounts` → `subscriptions` → `ledger_balances` → `invoice_counters`. A use case that needs several takes them in this order, so two transactions cannot deadlock.
- **Subscription writes.** `SELECT … FOR UPDATE` on the subscription row before any status change; webhook, verify call and jobs all go through the same transition function.
- **Admin edits.** Optimistic: the request carries `lock_version`; a mismatch returns `409 SUBSCRIPTION_STATE` with the current row.
- **Counters.** Only Lua scripts change Valkey counters and holds; Python never does read-modify-write on them.
- **No network inside a transaction.** Razorpay calls happen before the transaction opens or in a job after it commits, so a slow gateway never holds row locks.

### Properties

- For any sequence of postings the code builds, every transaction sums to zero and account balances equal the sum of their entries.
- `split_gst(g)` parts always add up to `g`, and taxable × 1.18 is within one paisa of `g`.
- `unused_credit` is between 0 and the amount paid, and falls as time passes.
- For any interleaving of reserve, commit, release and expire on one user, the day's committed plus held messages never exceed the limit, and `held` on a wallet is never negative.
- Applying the same usage event or webhook any number of times leaves the same rows as applying it once.
- `pick` never returns a lower-ranked grant than another live non-override grant.

## Decisions

All eight open items are settled, and the sections they touch have been updated to match. Two still need a check from outside before their feature ships: your chartered accountant signs off the GST choices before the first paid invoice, and the downgrade flow gets one run in Razorpay test mode.

| # | Item | Decision | Why |
| --- | --- | --- | --- |
| 1 | Upgrades and Razorpay add-ons | Do not depend on add-ons. An upgrade is one checkout: a new mandate at the new plan's full price, starting now. The period restarts that day, and the old period's unused days are refunded to the original payment method with a credit note. | [Razorpay's docs](https://razorpay.com/docs/api/payments/subscriptions/subscriptions/create-subscription) say add-ons are collected "as part of the authorisation transaction" but say nothing about a future `start_at`. This path uses only documented behaviour and asks the user for one approval, not two. Cost: the gateway fee on the refunded share is not returned, a few rupees per upgrade. |
| 2 | Manim and YouTube event names | `artifact.manim.rendered`, produced by llm-service (it owns Manim generation), and `file.youtube.ingested`, produced by file-service. Both carry `user_id`, `hold_id` and `succeeded`, and both are reserved through `CheckAndReserve` first. | They follow the existing pattern (`chat.message.created`, `chat.response.generated`) and come from the service that finishes the work. |
| 3 | llm-service changes | A v1 launch blocker, specified below. | Without provider-reported tokens, every cost and margin figure is wrong. |
| 4 | Pay as you Go vs a subscription | Credits are a wallet on top of any plan, not a plan that outranks one. A subscriber uses the plan first. When the plan denies a message (daily limit, or a model group it lacks such as Ultra) and the wallet has credit, that message is paid from credits at Pay as you Go prices. A user with credits and no paid plan is on Pay as you Go. | The Limit Behaviour sheet already says "upgrade / top up" at the daily limit. Nobody pays credits for what their plan covers, and storage, branches and other limits stay on the plan the user pays for. |
| 5 | Plan precedence for organisation members | Higher rank wins; on a tie the organisation's grant is used. When a member's org plan is equal to or higher than their personal plan, notification-service suggests cancelling the personal plan. Billing never cancels it. | A Max user who joins a college on Org Pro (30 messages a day) keeps what they pay for; whether to keep paying is their choice. Read the release plan's "org plan applies" as "unless the personal plan is higher". |
| 6 | GST details | (a) State is required at checkout, so every customer has an address on record and the place of supply is always their state. (b) Invoices carry paise, rounded half-up; rounding to the rupee happens only when filing returns. (c) Top-ups are taxed when paid, as an advance for services, with a tax invoice for each top-up; the wallet holds the taxable value. (d) The SAC code is a setting, `INVOICE_SAC_CODE`, defaulting to 998319 (other IT services). (e) A `GST_REGISTERED` setting: when false, documents are bills of supply with no tax. | (c) is the cautious reading. CBIC's [December 2024 voucher circular](https://www.taxmann.com/post/blog/cbic-issues-clarification-on-various-issues-pertaining-to-gst-treatment-of-vouchers) might allow taxing at use instead, which would avoid tax on credit that expires unused. Every candidate SAC code for software services is taxed at [18%](https://india-briefing.com/news/gst-compliance-for-saas-and-cloud-computing-in-india-explained-39021.html/), so the choice changes only the printed code. Registration is required above ₹20 lakh turnover; below that, (e) applies unless you register voluntarily. |
| 7 | Expired holds | The message is given back. The sweeper's `expire` now decrements the counters too, and if the usage arrives late anyway, `commit.lua` counts and bills it then. | A hold expires because our pipeline failed, not because of the user. A late event is still billed, so nothing leaks. |
| 8 | Supplier state | `SUPPLIER_STATE_CODE` is the state on your GST registration certificate (principal place of business): Bihar, `10`, if you register from Patna; Karnataka, `29`, if the company registers in Bengaluru. Customers in the same state get CGST + SGST; everyone else gets IGST. | The registration decides it, not where you live or where the servers are. |
